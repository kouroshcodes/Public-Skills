Run protocol

You are the runner. This file is the ledger: it is the record of where the work stands, and you are the only writer. Sub-agents never open it.

1. Read the whole file first

Every task, every state, every data-blocked-by (a space-separated list of task ids). A task is available only when EVERY listed blocker is done - otherwise leave it alone this round.

Any task already doing when you start was orphaned by a dead runner - no agent of yours owns it. Verify its acceptance criterion now: met, settle it done; not met, reset it to todo (its half-applied edits are now yours to inherit - diff before redispatching).

2. Claim before you dispatch

For each available task, edit this file: data-state="todo" becomes data-state="doing" on that task's article. Match on the literal string data-id="T3" data-state="todo" so the edit hits exactly one task. If the task has a data-issue, mirror the claim with gh issue comment <n> --body "Claimed by worklist runner.". Claim every task in the round before spawning anything, so nothing is picked up twice.

3. Fan out - AT MOST 3 AGENTS, ONE BROWSER

This is an 8GB Mac and it HARD-CRASHED on 2026-08-08 doing this step wrong. Six agents were spawned in one message against one shared dev server. The dev server was never the problem - it was ~3.2GB. Each agent also spawned its own headless Chrome (~0.5-0.8GB) and its own tsc (~1.5GB each, three concurrent at peak). The box went to 13.9GB swap and died. Do NOT spawn one agent per task.

  • Cap the round at 3 agents, and only ONE may drive a browser. The other two must be text-only - docs, a test, a grep audit, a code edit with no visual check. The browser count is the real constraint, not the agent count; two headless Chromes in one round is what kills the box.
  • You start ONE dev server before dispatching, and say so in every prompt: never npm run dev, never start a second, never kill it.
  • Forbid per-agent tsc, vitest, next build and npm install in the prompt. Run ONE gate centrally after the round with no browser open. Biggest single win - three agents each running tsc is ~4.5GB of pure duplication.
  • Watch memory_pressure / vm_stat, not the agent count. Below ~1.5GB free, stop dispatching and kill something.
  • Before killing an agent, check what it owns. One held a seeded account in the LIVE database - killing it blind would have orphaned production data. Message it to tear down first, then stop it. Killed agents also leave half-applied edits that break the central gate for everyone else.
  • More tasks than slots? Run several rounds. A queued task costs nothing; a crashed machine costs the whole session.

Give each agent the task's context, files, and acceptance criterion copied out of this file - it cannot see this file or your conversation. Tell it to report back what it changed, whether the acceptance criterion is met, and to be explicit about what it did NOT verify.

4. Verify, then settle the ledger

An agent's word is not evidence. Check the acceptance criterion yourself - read the diff, run the check. Check the artifacts too: an agent once reported four both-theme screenshots that were all ZERO BYTES, and its "verified in both themes" claim was simply false - stat anything an agent cites as proof. An agent that says plainly what it did NOT verify is more useful than one that claims a clean pass; treat an unqualified "all criteria met" as a prompt to look harder, not less. Then edit this file once per task:

  • criterion met: data-state="doing" becomes data-state="done", and if there is a data-issue, gh issue close <n> --comment "<what shipped>"
  • criterion not met: data-state="blocked", put the reason in that task's <span class="note">, and if there is a data-issue, comment the reason on it rather than closing. (blocked means attempted and failed for the noted reason - a task merely waiting on its data-blocked-by stays todo.)

5. Next round

Finishing a task can unblock others. A blocked task whose noted reason was transient - a flaky test, an agent that ran out of context, memory pressure - gets ONE retry: reset it to todo and append "(retry)" to its note. A reason that names a durable obstacle (needs auth, needs a decision, needs data that doesn't exist) stays blocked. Go back to step 1 and repeat until every task is done or durably blocked.
